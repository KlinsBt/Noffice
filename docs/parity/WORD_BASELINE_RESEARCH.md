# Word baseline measurements, September 10, 2026

The pinned Word 16.0.4627.1000 reference was measured with the Microsoft Print to PDF printer. The authored `word-baselines.docx` fixture contains 18 Arial paragraphs: repeated 10/20/30pt runs, 1.5-line variants, 40pt paragraph marks and 50pt minimum variants. Source SHA-256 is `431950979466304232e873a4a430fe55e85da807d470e4a9904c05b93cc562b2`. Font/executable hashes and original COM observations are in `tests/fixtures/native-word-baselines.json`. Current runs remain under `.local/word-baselines`.

`scripts/report-word-baselines.py` extracts PDF text matrices and subtracts the corresponding native COM character-line origins. Repeated single-spacing offsets are approximately 9.36-9.38pt at 10pt, 18.37pt at 20pt and 27.92-27.95pt at 30pt. These are measurements of two native coordinate APIs, not a universal ascent ratio. Adjacent COM origins also vary with run size: do not assume every reported character origin is an exact paragraph border-box origin.

The second native XPS export reports 10pt text as 9.96, 20pt as 20.04 and 30pt as 30 in its glyph rendering sizes; its glyph origins agree with PDF to the reported precision. Thus the observed size/position quantization is present in both native export paths. XPS contains embedded font resources and remains local test evidence, not a distributed fixture.

The browser probe (`scripts/probe-word-baselines.mjs`) measures normal line height, baseline and canvas font bounds at the same sizes and at a large effective size. Chromium caps the requested large probe at 10,000 CSSpx. At that size normal height is 11,499px, the DOM baseline is 9,216px, and canvas ascent/descent are 9,053/2,119px. At normal sizes these values are rounded differently. Installed Arial's font tables report unitsPerEm 2048, hhea ascent/descent/gap 1854/-434/67 and Windows ascent/descent 1854/434. A font-family-specific runtime offset has not been justified by these measurements.

An exploratory read-only GDI printer-DC probe under `scripts/probe-word-printer-fonts.ps1` records a 600 DPI printer and integer font metrics in `gdi-metrics.json`. GetTextFace reports Arial, and GetFontData produces SHA-256 `b3658eadae55e682b5f69eb64c439c1ecc8f196c0bb8d4756d145d13bc86476a`, exactly matching installed arial.ttf for all three sizes. The hinted printer ascent/descent/external-leading triples are 74/18/3, 150/37/5 and 224/54/8 pixels respectively. These still do not reproduce every Word glyph-origin offset through a simple ratio. No printer settings were changed or print job submitted. It is not production code or a passing baseline contract.

References checked September 10: [Microsoft TEXTMETRIC fields](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-textmetrica) distinguish ascent, descent and external leading; [W3C inline layout](https://www.w3.org/TR/css-inline-3/) describes the role of font metrics and line-height in inline layout. Neither reference establishes Word's exact rendering coordinates.

The measurable product fix from this investigation is separate: the paragraph mark must not supply a minimum strut for the tested nonempty single lines. A 40pt mark with 8/10pt text previously produced nearly 60pt instead of 17.25pt. Semantic per-run sizes now survive exclusion of that strut, and clearing the paragraph restores the 40pt mark for empty-line typing. See [the feature contract](contracts/W-TEXT-UNIFORM-LINES.md#large-paragraph-mark-subset).

Next research: isolate coordinate scaling, hinting/quality and Word line-origin conventions; compare repeated sizes against actual native screen/layout coordinates as well as exported glyph matrices. Keep source origin, line advance, font ascent and output rounding separate. Do not apply a constant quarter-point translation or certify wrapped text from single-line measurements.

## Follow-up: relative leading placement

The repeated-size investigation exposed a larger, independent error in uniform text: the old browser branch moved a 10pt line's text by 2.25pt when changing 1.5-line spacing to Double. Native Word leaves that text position unchanged. A 50pt minimum instead adds 38.5200pt above the text relative to the original paragraph; the measured browser fix adds 38.4961pt. Three independently edited native exports now verify the fix. These are same-font differences across spacing edits, not absolute baseline equivalence. [Contract and reproduction](contracts/W-TEXT-UNIFORM-LINES.md#uniform-single-line-leading-placement).

Additional official research: [OpenType OS/2 metrics](https://learn.microsoft.com/en-us/typography/opentype/spec/os2) distinguishes typographic line-spacing recommendations from Windows clipping metrics; [Windows font metrics guidance](https://learn.microsoft.com/en-us/windows/win32/menurc/fonts-and-font-metrics) likewise does not define Word's private layout algorithm. Neither supports substituting a fixed Arial baseline correction. The next controlled measurement is homogeneous wrapped-line placement before general mixed-run fragmentation.

## Wrapped-line follow-up

The reduced 35-word fixture now matches seven soft-wrap and three hard-break identities across source/Double/minimum/Single. Its first wrapped line retains the same paragraph origin across spacing edits; shifts are 0pt for Double/Single and 6.47998pt for an 18pt minimum. Browser natural-height top/bottom alignment gives 0pt and 6.50391pt. Later hard-break paragraph coordinates still show four deltas outside 0.15pt, up to about 0.288pt; all 27 secondary coordinates remain visible diagnostics. Passing exact native-rendered exported PDFs does not close those browser coordinate gaps. The runtime does not apply a universal baseline offset. [Evidence and remaining work](contracts/W-TEXT-UNIFORM-LINES.md#uniform-wrapped-line-subset).
